| 总线 | Classic CAN，1 Mbps，sample point 0.75 |
| 机械臂 | 标准 Piper，无 X/L 后缀，剪刀式示教手柄 |

| 布局 | 用户确认底座约 70 cm，同向朝工作区域 |

两根 CAN 线的 H/L 最终都相对最初接法交换后才正常。此前 CAN3↔CAN4 的外部对测在 125 kbps 和 1 Mbps 均通过；不能把本机 TX echo 当作硬件 ACK 或机械臂反馈。

两臂最初处于示教主臂状态：静止时可能不发报文，`0x155/156/157` 是主臂输出，不是普通实际状态反馈。切 follower 后使用 `0x2A5/2A6/2A7` 实际角度、`0x2A1` 状态和 `0x261..266` 驱动使能/故障位。左臂在 `470#FC00000000000000` 后立即产生标准反馈，后续物理重启也验证了持续反馈；右臂按同样角色配置后完成实机动作。腕部示教按钮会切走 CAN 控制，不能忽略该变化。

## Home、抬升及结果

[原始 home](../../artifacts/piper-commissioning-20261023/bimanual-lift-8cm/home-poses.json) 保留，没有因重启、下垂或试验而覆盖：

```text
J1..J6，单位 degree
left  = [ 1.216, -2.938, 1.732,  5.621, 14.296, -23.730]
right = [-2.786, -2.310, 1.776, -1.117,  7.395,   3.187]
```

左 home 来自用户轻移后放回的最后完整主臂输出；右 home 为 44 组稳定观测中位数。原始采样与派生量分开保存。两臂 J2/J3 略越读回的名义目标范围，**未将 home 自动截断成零**。固定 SDK 的关节限位检查是本地可选项，默认关闭；设备在 MIT 下是否按读回范围硬裁剪没有已确认保证，因此本轮仅使用明确的起点/终点路径范围，不修改设备限位或零点。

用户先认可 30 mm 可视化提案，后明确要求更明显的抬升。最终采用相对原 home 法兰上抬 80 mm 的 [双臂目标](../../artifacts/piper-commissioning-20261023/bimanual-lift-8cm/targets.json)：

```text
left  ≈ [ 1.216, 6.977, -15.598,  3.753, 21.688, -21.770]
right ≈ [-2.786, 7.292, -15.601, -0.549, 15.170,   2.610]
```

目标用已核对的标准 Piper MDH / SciPy 求解，保持法兰朝向，理论升高 80 mm。第一次成功运行的平台实际关节角经同模型 FK 估算：相对该轮真实起点，左升约 **8.26 cm**，右升约 **8.92 cm**；相对原始 home，约 7.11 / 7.34 cm。它们是关节反馈的 FK 估计，不是外部测量。

执行参数为纯 PD：`Kp=20, Kd=1, v_des=0, t_ff=0`，100 Hz，20 秒去程、8 秒停留、20 秒回程。没有主机重力前馈。SDK 的 8-bit 力矩编码不能精确表达数学零，记录的是输入命令 0，不声称物理力矩严格为零。

回程采用 **3° 关节误差容差**，两次均确认回位后再发送禁能并等待六轴新反馈。禁能后手臂会在垫上松弛，下垂后的角度可以与 home 相差更多；不要拿禁能后的最后一帧反推“回程没有进入容差”。本轮不是精密定位验收。

## 真正起作用的发送修正

早期程序只在起始时发一次模式帧，且速度字段为 0：有使能和刚度反馈，但持续变动的位置参考没有正常被跟随。最后成功实现按官方 SDK 的持续设置模式行为，在**每个 100 Hz 周期**先发：

```text
151#010432AD00000000
```

然后发 J1..J6 的 `0x15A..0x15F` MIT 帧。速度字段恢复 SDK 默认 50。**这两项修改一起生效，未分别隔离因果；不要宣称仅一个字段已被独立证明为根因。**

之前的 0.15 rad/s 中止和 3° 跟随误差中止均由用户明确要求去掉；本轮把速度/跟随误差作为记录，仍保留通信、时间戳和驱动故障检查。首次 Kp 从 0 慢爬时，受协议量化影响，在首次停止前实际 P 编码始终为 0，不能把那轮称为 PD 保持成功。
